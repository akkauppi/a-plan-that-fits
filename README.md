# A plan that fits

**What makes a plan work?** An interactive exploration of planning constraints
and a solver's potential role in understanding them.

[Try the browser tour](https://akkauppi.github.io/a-plan-that-fits/) ·
[Research question and related work](docs/research-framing.md) ·
[Run locally](#run-locally)

[![Checks](https://github.com/akkauppi/a-plan-that-fits/actions/workflows/check.yml/badge.svg)](https://github.com/akkauppi/a-plan-that-fits/actions/workflows/check.yml)

## Predict, check, explain

Choose hypothetical parcel lockers and supply depots on a real walking map of
Tapiola–Otaniemi, Espoo. Residents need a walk of at most **500 m** to a locker.
The supply network must respect shared capacities and keep working when one
selected depot closes.

Try a plan yourself, ask the solver to check it, and explore why the answer
changes when a rule changes. No programming knowledge is needed.

A **constraint** is a rule a plan must meet. A **constraint solver** searches for
choices that satisfy the rules together; it can also establish that none work
within the model. This tour uses **Z3**, a general-purpose solver running in the
browser through WebAssembly. Other solving approaches can address this problem
too. [Introduction to constraint solving](https://developers.google.com/optimization/cp) ·
[About Z3](https://www.microsoft.com/en-us/research/publication/z3-an-efficient-smt-solver/).

The tour invites you to:

1. Distinguish geographic inputs, planning assumptions and decisions.
2. Build a plan from an empty selection of locker and depot candidates.
3. Examine what a depot outage changes.
4. Inspect a solver-selected plan and the scope of its answer.
5. Change a rule and explain what you learned.

A nearby connection alone does not establish a capacity-feasible network.
A feasible answer is one working assignment, not necessarily the best one.
An impossibility result concerns the stated candidates and rules.
A timeout, cancellation or error gives no feasibility conclusion.

## An exploratory prototype

The research question is whether this game and its explanations help
nontechnical users understand interacting planning requirements and solver
feedback. **Learning benefits have not yet been evaluated in a participant
study.** The app collects no participant responses or analytics.

This is a reproducible demonstration and a starting point for evaluation,
not an operational locker-siting tool or a new solver algorithm. The
[research notes](docs/research-framing.md) separate current evidence, related
science and a proposed learning study.

An optional cross-check compares Z3 with independent exhaustive JavaScript
search on the same question. Timings are tucked into diagnostic details.
Agreement supports implementation consistency; a single scene and timing pair
do not establish general solver superiority.

## Real geography, explicit assumptions

The frozen case contains 33 published population cells with 8,554 residents,
24 hypothetical locker candidates and six hypothetical depots. The game asks
for ten lockers and four depots; the solver can also explore other budgets.

Walking eligibility follows directed paths, including a connector from each
cell's representative point. The 500 m limit stays fixed. The locker shortlist
is generated by a documented geographic procedure, not selected by Z3.
Sites, parcel demand, capacities and drone rules are illustrative assumptions.
Cell-point coverage is not a guarantee of access from every home, and the
supply lines are not approved flight routes.

## Run locally

Use Node.js **24.15.0** (see [.nvmrc](.nvmrc)).

```sh
git clone https://github.com/akkauppi/a-plan-that-fits.git
cd a-plan-that-fits
npm ci
npm run dev
```

Open the localhost URL printed by Vite. The first visit may reload once to
enable browser isolation. Initial loading includes about 34 MB of Z3
WebAssembly and 9 MB of geography. No Python, API server, account, map key,
external tiles or runtime CDN is needed.

For a production build, run `npm run build`, then `npm run preview`.
Use HTTPS or localhost; opening `index.html` directly with `file://` will
not work. This is a browser-local application, not an offline installation.
See [browser requirements and hosting](docs/development.md).

## Reproduce and contribute

```sh
npm run check
npm run data:audit-complexity
npx playwright install chromium
npm run test:e2e
```

The checks cover types, byte-identical data regeneration, real Z3 cases,
small-instance oracles, independent feasible-plan verification and the
production build. Browser tests cover desktop and tablet journeys under a
static-site subpath.

Start with [contribution guidance](CONTRIBUTING.md). For implementation work,
read [AGENTS.md](AGENTS.md) and the [continuation handoff](docs/agent-handoff.md).
Prefer improvements to understanding and explanation over adding more demos.
Generation from unprepared locations is deferred.

Feedback is welcome through [GitHub issues](https://github.com/akkauppi/a-plan-that-fits/issues).
For research or teaching references, use [CITATION.cff](CITATION.cff) and record
the Git commit and geographic snapshot used.
